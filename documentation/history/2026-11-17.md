New spec: the real generator in a throwaway repository.
- **ESLint 10 needed a lockfile refresh**: the hoisted `@typescript-eslint/utils` was held at 8.48.1, which throws "Class extends value undefined" under ESLint 10 (the failure on PR #6). `bun update @typescript-eslint/utils` moved it to 8.72.2.

# 2026-11-17 (later): Issue #11, where the transcription goes

Branch `feat/output-options`. PR #13 (the dependency updates above) is merged.

## Accomplished

Three settings, all off or empty by default, so nothing changes for a current user:

- `outputFolder`: one vault folder for every transcription file. Declarative `folder` control (suggester, since 1.13.0 = `minAppVersion`). Created on demand, one level at a time.
- `outputFilePrefix`: text in front of the file name, with or without an output folder. The settings tab refuses characters a file name cannot hold.
- `insertIntoNote`: the text goes into the target note, in a paragraph after the image's embed, else at the cursor; no file is written.

And the notice for a single image says where the text went (`Output: <path>`, `Inserted into: <note>`, or `Skipped ..., already transcribed`) and stays 10 seconds. `TranscriptionResult` has `skipped` and `inserted`.

## Decisions

- **The prefix is its own setting**, not tied to the output folder as in the issue's patch.
- **Insert mode never applies to folder transcriptions.** A folder of 200 images inserted at the cursor of whatever note is active is a surprise; folders always write files.
- **Insertion goes through the editor when the note is open**, else `vault.process`. A file write under an open editor would discard text that is not saved yet, and a transcription takes seconds.
- **The embed is found in the text at write time**, not from the metadata cache: after the first insertion of a batch the cache's line numbers are stale. New parser in `utils/note-embeds.ts` (alias, subpath, angle brackets, percent-encoding, fenced code). The editor menu still uses its own two regexes: an embed with a size (`![[a.png|300]]`) does not get the "Transcribe this image" item. Not changed here.
- **Same image name, one output file**: accepted and documented, not disambiguated.
- **Business rules changed with approval**: Output Naming rewritten; Insert Into The Current Note and Result Notice added.

## Verification

tsc clean, lint clean, 217 tests (62 new), rule floor intact, build green.

Live check in a real vault (Obsidian 1.15.0), with the model call stubbed, settings changed in memory only, test files in a scratch folder (deleted after), and the released 2.1.1 build restored at the end:

- The three rows are in the settings definitions (`folder`, `text`, `toggle`); a prefix with `/` is refused and nothing is saved.
- File mode: a file lands in a new nested output folder under the prefixed name, with the frontmatter tags; a second run is skipped with no model call.
- Insert mode, note closed: two parallel insertions each land after their own embed (`![[a.png|200]]` and `![alt](media/b.png)`), no tags.
- Insert mode, note in Live Preview: after the embed, then at the cursor; text typed just before is kept; the text reaches the file by itself.
- Insert mode, note in Reading view: written to the file (after the embed, then at the end).
- "Transcribe current image" on an image tab with insert mode on: a file, and the notice `Transcribed scan-two.png. Output: <path>`.

## Lessons

- **A Reading view has an editor object, and a write through it is never saved** (checked: still absent from the file after 3.5 s and after the tab closed). Hence `getMode() === 'source'` in `findEditor`; other modes go through `vault.process`.
- **Templater rewrites a note it has just seen created.** With "trigger on file creation", `overwrite_file_commands` calls `vault.modify` with the content it read at creation, about 2 s later. A test that creates a note and writes to it at once sees its write reverted. It looked like a plugin bug for a while; wait a few seconds after `vault.create` in a live test. A user who inserts into a note created in the last 2 seconds can lose the insertion the same way: not handled.
- **One `plugin:reload` failed once** from the long-running 2.1.1 instance to the new build ("Attempting to register an existing view type image-transcriber-whats-new" on the next try). Not reproduced: 2.1.1 → new and new → 2.1.1 reloads both pass after that. Cause unknown; the first error was not captured.

## Open

- Not checked live: the look of the three rows in the settings pane (the `folder` suggester above all), the 10 second duration, the editor menu and file explorer menu paths (only the command and the service were driven), and that Reading view repaints after the write.
